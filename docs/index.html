DUT는 공개된 AXI DMA IP이고, RTL 설계는 본인 작업이 아닙니다. 검증 환경, 테스트, CI, 자동화는 직접 만들었습니다. 저장소에는 RTL을 넣지 않았습니다.

01 · DUT와 검증 환경

무엇을 검증했나

CPU가 AXI4-Lite로 원본 주소, 대상 주소, 길이를 쓰고 시작하면, RDMA가 메모리에서 읽은 데이터를 8비트 lane 8개 덧셈기로 가공하고 WDMA가 다시 메모리에 씁니다. TB는 세 인터페이스를 각각 agent로 감싸고, 메모리 모델과 scoreboard로 결과 바이트와 AXI 규칙을 모두 확인합니다.

단계적 검증: unit → IP top

  • 하위 블록 unit TB 5개: fifo(깊이 64), fifo_d4(full/empty 경계), skid, adder(32b lane), adder8(8b lane)
  • unit 테스트 6종: smoke, rand, backpressure, trickle, fixed_side, post_reset
  • IP top TB: AXI4-Lite master + AXI4 slave 메모리 모델로 실제 DMA 동작 전체를 검증
  • 파일 하나에 클래스 하나. RAL 대신 레지스터 맵 상수와 write_reg()/read_reg()

Top 테스트 11종

  • smoke, small, large, rand
  • size_edge (1 / 16 beat 경계), 4kb (4KB 경계 분할)
  • backpressure (W/AR/R/B 랜덤 지연), aw_backpressure (AWREADY 지연)
  • irq, reg_bitbash, reg_reset
  • AXI·valid/ready 프로토콜 SVA는 인터페이스에 상주
02 · 대표 성과

BUG-002: AWREADY가 늦으면 WDMA가 멈춤

OPEN · RTL

W beat가 AW 수락보다 먼저 나가고, 그 beat를 세지 않아 WLAST가 3 beat 늦게 나옴

발견
AXI slave가 AWREADY를 늦추는 dma_aw_backpressure_test. 다른 테스트는 AWREADY를 바로 주기 때문에 드러나지 않던 경로입니다.
증상
16 beat burst의 WLAST가 19번째 beat에 나오고, 이후 burst가 모두 밀립니다. B 응답 수가 끝내 맞지 않아 ap_done이 나오지 않습니다.
원인
WVALID가 W 상태 머신과 무관하게 FIFO 상태만 따릅니다. W FSM이 아직 IDLE이면 burst 카운터가 0에 묶여 있어, 그동안 수락된 3 beat가 세어지지 않습니다.
수정안
WVALID = s_valid & w_s_run_w, s_ready = WREADY & w_s_run_w
영향
Zynq HP 포트나 interconnect가 AWREADY를 늦추면 실제 보드에서도 멈출 수 있습니다. 지금 보드 구성(HP0 직결)에서는 AWREADY가 바로 돌아와 재현되지 않았습니다.
AW 수락 전에 나간 beat (카운트 안 됨) 정상 카운트된 beat 실제 WLAST slave가 기대한 WLAST

05 · Coverage

커버리지 모델

Top: cg_job, cg_burst

  • 전송 길이: 1 / 2–15 / 16(최대 burst) / 17–511 / 512(정확히 4KB) / 그 이상 beat
  • 더할 값: 0, 1, 255 경계, 그리고 무시돼야 하는 상위 비트가 켜진 경우
  • 원본·대상 주소의 4KB 경계 통과 여부
  • burst 방향 × 길이, 방향 × 4KB 분할 cross

Unit: cg_beat, cg_cycle

  • lane 값 0 / max, carry 발생 여부
  • 입출력 valid/ready 상태 4가지와 그 cross
  • 3 사이클 연속 전송(back-to-back) 같은 시퀀스 bin

XSim 2022.2에서 찾아 우회한 문제

  • 넓은 범위의 dist가 심하게 치우침 → 경계값 편향을 절차적으로 생성
  • coverpoint 식 안의 폭 변환을 잘못 계산 → 미리 계산한 변수를 샘플링
  • bin 상한 $가 모든 샘플을 한 bin에 넣음 → 상한을 명시
  • 함수 결과에 비트 선택 불가, small/large 등이 키워드 → 임시 변수, bin 이름 변경
  • xcrg가 기존 보고서에 덧붙임 → 병합 전에 출력 디렉터리를 비움

07 · Embedded C

ARM bare-metal C로 HW/SW co-verification

JTAG로 레지스터를 직접 쓰는 시험은 하드웨어만 확인합니다. 실제 드라이버 경로까지 확인하려고, 같은 7개 시험을 Cortex-A9에서 도는 C 프로그램(Vitis standalone BSP)으로 다시 만들었습니다. 프로그램이 데이터를 준비하고, DMA를 구동하고, 결과를 스스로 판정합니다.

cache coherency 처리

DMA가 연결된 HP0 포트는 CPU cache와 일관성을 보장하지 않습니다. 참조 C 예제는 D-cache를 통째로 껐지만, 이 프로그램은 cache를 켠 채로 필요한 범위만 처리합니다.

  • DMA 전: 원본과 대상 범위를 Xil_DCacheFlushRange로 DDR에 내보냄 (대상의 dirty line이 DMA 결과를 덮지 않게)
  • 레지스터 설정 → IDLE 확인 → ap_start → DONE 대기 (1초 넘으면 HANG)
  • DMA 후: 대상 범위를 Xil_DCacheInvalidateRange로 비우고 바이트마다 비교

결과 두 경로로 교차 확인

프로그램은 결과를 UART로 출력하고, 같은 내용을 DDR의 mailbox 구조체에도 씁니다. 호스트 스크립트는 JTAG로 mailbox를 읽고 UART 로그와 판정이 같은지 확인합니다. 둘이 다르면 전체를 실패로 처리합니다.

  • xsct: XSA → standalone BSP → ELF 빌드
  • xsdb: 비트스트림, PS 초기화, ELF 다운로드와 실행
  • Python: mailbox 해석, UART 수신, 판정, result.json

1MB 전송에서 DMA는 787 MB/s로, 64비트 × 100MHz 이론값(800 MB/s)의 98%이고 CPU memcpy보다 2.2배 빠릅니다. 작은 크기에서 CPU가 빨라 보이는 것은 원본이 아직 cache에 남아 있기 때문이라, 공정한 비교는 L2(512KB)보다 큰 1MB뿐입니다. DMA 시간에는 DONE 폴링 지연이 포함됩니다.
