AXI DMA IP UVM 검증 환경과
AI Agent 기반 검증 자동화

AXI4-Lite 레지스터, AXI4 read/write DMA, AXI-Stream 연산기로 이루어진 DMA IP를 Vivado XSim에서 UVM으로 검증했습니다. top 테스트벤치는 RAL 레지스터 모델, RTL을 매 클럭 따라가는 predictor, 모니터 기반 scoreboard로 구성하고, 결함을 일부러 넣어 검사가 실제로 잡는지 확인합니다. 반복 작업은 LLM Agent가 MCP로 시뮬레이터를 다루도록 자동화하고 판단과 승인은 사람이 맡았으며, 모든 push는 Jenkins 회귀와 sign-off 기준 11개로 확인합니다. 이 과정에서 RTL 기능 버그 7건과 설계 노트 3건을 찾아 재현 테스트와 함께 등록했고(RTL은 고치지 않음), Zynq 보드의 실제 DDR에서 1MB 전송까지 JTAG 시험과 ARM bare-metal C 프로그램 양쪽으로 동작을 확인했습니다.

DUT는 외부 AXI DMA IP이고, RTL 설계는 본인 작업이 아니며 읽기 전용으로 다뤘습니다. 저는 검증 방향과 범위, 판정 기준, 사양 해석을 정하고 사람 확인 지점(RTL 버그 등록, 검사 기준선 변경, 커밋)을 승인했습니다. 코드 구현과 검토는 직접 구성한 Claude Code 에이전트(구현 담당과 검토 담당 분리)가 했습니다. 저장소에는 RTL을 넣지 않았습니다.

01 · DUT와 검증 환경

무엇을 검증했나

CPU가 AXI4-Lite로 원본 주소, 대상 주소, 길이를 쓰고 시작하면, RDMA가 메모리에서 읽은 데이터를 8비트 lane 8개 덧셈기로 가공하고 WDMA가 다시 메모리에 씁니다. TB는 세 인터페이스를 각각 agent로 감싸고, 판정은 모니터가 본 것으로 합니다. predictor가 모든 레지스터 읽기 값과 interrupt 핀을, scoreboard가 burst 목록과 W beat, 결과 메모리를 확인합니다.

단계적 검증: unit → IP top

  • 하위 블록 unit TB 5개: fifo(깊이 64), fifo_d4(full/empty 경계), skid, adder(32b lane), adder8(8b lane)
  • unit 테스트 7종: smoke, rand, backpressure, sparse_input, fixed_value, post_reset, single_beat
  • IP top TB: AXI4-Lite master + AXI4 slave 메모리 모델로 실제 DMA 동작 전체를 검증
  • 재사용 VIP 3종(stream, AXI4-Lite, AXI4 slave)은 DUT를 모르는 코드. 파일 하나에 클래스 하나

Top 테스트 21종

  • 기본: smoke, short_job, long_job, rand, size_edge, 4kb_cross
  • 지연: backpressure, aw_backpressure, aw_wait_after_job, slow_b
  • 레지스터와 인터럽트: reg_reset, reg_bitbash, irq, irq_ready, busy_reg_write
  • 제어와 리셋: start_busy, auto_restart, reset, reset_mid_job, size_128mib
  • 검사기 자체 시험: checker

top 테스트벤치의 판정 구조

  • RAL 레지스터 모델: 정의되지 않은 비트도 RO 필드로 넣어 32비트 전체를 비교. 레지스터 테스트는 UVM 내장 sequence로 reset 값 10개와 bit-bash 비교 1,024회
  • predictor: 버스 handshake만 입력으로 받아 RTL 상태를 매 클럭 따라가는 사이클 모델. 모든 AXI-Lite 읽기 값과 interrupt 핀을 허용 구간 없이 비교
  • 모니터 기반 scoreboard: burst마다 주소·길이를 기대 목록과, W beat마다 데이터와 strobe를, 마지막 B 뒤에 대상 메모리를 바이트 단위로 비교. 작업 없이 생긴 버스 활동과 끝나지 않은 작업도 오류
  • checker self-test: 결함 5종을 일부러 넣어, 잡아야 하는 검사가 실제로 오류를 내는지 확인. 결함을 넣지 않으면 이 테스트가 FAIL하는 것(음성 대조)도 확인
  • SVA: AXI·valid/ready 규칙은 인터페이스에, ap_ctrl_hs handshake 규칙 7개는 bind로 붙여(RTL 수정 없음) 모든 top 테스트에서 검사
  • 테스트 중간 리셋: 진행 중인 레지스터 접근이 끝난 뒤 리셋을 걸고, predictor·scoreboard·slave 모델이 리셋을 따라감
02 · RTL 버그

BUG-002: AWREADY가 늦으면 WDMA가 멈춤

OPEN · RTL

W beat가 AW 수락보다 먼저 나가고, 그 beat를 세지 않아 WLAST가 3 beat 늦게 나옴

발견
AXI slave가 AWREADY를 늦추는 dma_aw_backpressure_test. 다른 테스트는 AWREADY를 바로 주기 때문에 드러나지 않던 경로입니다.
증상
16 beat burst의 WLAST가 19번째 beat에 나오고, 이후 burst가 모두 밀립니다. B 응답 수가 끝내 맞지 않아 ap_done이 나오지 않습니다.
원인
WVALID가 W 상태 머신과 무관하게 FIFO 상태만 따릅니다. W FSM이 아직 IDLE이면 burst 카운터가 0에 묶여 있어, 그동안 수락된 3 beat가 세어지지 않습니다.
수정안
처음에는 WVALID와 s_ready를 W RUN 상태로만 거르는 안을 냈습니다. 다시 검증해 보니 이것으로는 부족했습니다. 작업을 한 번 끝낸 뒤에는 W 상태 머신이 RUN에 남아 BUG-003이, B 응답이 느리면 BUG-004가 그대로 남습니다. AW FIFO가 비지 않았고 W→B FIFO에 자리가 있을 때만 W를 내보내는 조건으로, 세 버그를 함께 닫는 안을 다시 적었습니다.
영향
Zynq HP 포트나 interconnect가 AWREADY를 늦추면 실제 보드에서도 멈출 수 있습니다. 지금 보드 구성(HP0 직결)에서는 AWREADY가 바로 돌아와 재현되지 않았습니다.
AW 수락 전에 나간 beat (카운트 안 됨) 정상 카운트된 beat 실제 WLAST slave가 기대한 WLAST

RTL은 고치지 않고 재현 테스트를 known_fail로 등록했습니다. CI는 계속 초록색이고, 누군가 RTL을 고치면 그 테스트가 XPASS가 되어 CI가 알려 줍니다.

가설에서 판정까지

  • BUG-003~007은 에이전트가 RTL을 읽고 세운 가설 7개를 하나씩 directed test와 파형으로 판정한 결과이고, 판정 기준과 버그 등록 승인은 사람이 맡았습니다. 7개 모두 시뮬레이션에서 확인됐고, 6개는 버그 5건으로(원인이 같은 2개는 BUG-005 하나), 1개는 설계 노트(NOTE-002)로 정리했습니다.
  • 재현 테스트는 seed 3개 이상에서 같은 결과를 냈습니다. 테스트가 노린 상황에 실제로 도달했는지를 별도 검사로 확인하고, 실패 로그에 TB 쪽 문제가 섞이지 않았는지도 gate에서 확인합니다.
  • 이전 판단도 고쳤습니다. BUG-001의 영향을 처음에는 "낮음"으로 적었지만, 작업 도중 리셋에서 그 경로가 실제로 걸린다는 것을 BUG-006으로 확인했습니다.
  • 버그마다 증상, 원인, 파형 시각, 재현 명령, 수정 제안, 보드 영향을 문서로 남기고, 수정 여부는 RTL 담당자 결정으로 남겼습니다.

CI와 같은 스크립트를 부릅니다. 등록된 TB·테스트 이름만 받고, 소스 파일을 쓰는 도구는 없으며, 로그 접근은 출력 디렉터리 안으로 제한합니다. git worktree별 잠금으로 여러 Agent가 동시에 써도 섞이지 않습니다.

검증 결과를 믿을 수 있게 하는 장치

  • 검사 목록 기준선: 검사가 줄거나 억제 구문이 늘면 실패. 기준선은 사람이 승인할 때만 바뀜 (57 → 69 → 123개)
  • 결과 출처 기록: 모든 결과에 커밋, 수정 여부, RTL 내용 해시, 재실행 명령. 출처가 다른 결과가 섞이면 sign-off FAIL
  • 단계 gate: 단계를 끝냈다는 판정은 글이 아니라 스크립트 결과로. 재설계 7개 단계를 각각 gate PASS로 닫음
  • hook: RTL 수정, 시뮬레이터 직접 호출, 근거 없는 known_fail 등록을 차단. hook 자체의 회귀 테스트 50개
  • 장치의 시험: 검사 하나를 일부러 약하게 바꾸자 hook이 바로 알렸고, 검토 에이전트가 수정을 요청함

Sign-off 기준: 11개 기준을 결과 파일로 자동 판정

"검증이 끝났다"를 사람의 감이 아니라 기준으로 정했습니다. signoff.py가 회귀, 커버리지, 타이밍, 보드 결과 파일을 읽어 판정하고, Jenkins는 모든 빌드 끝에 이 판정을 남깁니다. 기준을 못 채우면 빌드가 UNSTABLE이 됩니다. 처음 적용한 빌드 #27에서 smoke sign-off PASS였고, 재설계 뒤에는 브랜치 빌드 #11이 smoke sign-off PASS, full 빌드 #12가 nightly sign-off PASS입니다.

06 · ML Regression

학습한 커버리지 모델로 회귀 실행 76% 절감

회귀를 얼마나 돌려야 커버리지가 닫히는지를 경험으로 정하지 않고 데이터로 정했습니다. 실행 820회(당시 등록된 TB·테스트 조합 41개 × seed 20개)의 bin 적중 기록으로 테스트마다 bin을 칠 확률을 학습하고, 그 모델로 가장 적은 실행으로 커버리지를 닫는 회귀 계획을 만듭니다. 76%는 nightly 205회를 49회로 줄인 값이고, 학습에 쓰지 않은 seed에서 100% 도달 확률 99.1%를 확인한 계획 기준입니다.

방법

  • 데이터: 실행마다 기능 커버리지 DB를 xcrg로 풀어 bin별 적중 여부를 수집
  • 모델: (테스트, bin)마다 seed 하나로 그 bin을 칠 확률 p를 Beta-Bernoulli 사후 평균으로 추정
  • 계획: bin을 놓칠 확률 ∏(1−p)n의 합이 0.05 아래가 될 때까지, 실행 1초당 기대 커버리지 증가가 가장 큰 테스트에 seed를 하나씩 추가 (greedy)
  • 안전장치: 모든 테스트를 1회 이상 포함. 커버리지에 안 잡히는 레지스터 검사와 알려진 버그 재현을 계속 확인

검증 방식

학습에 쓴 seed로 평가하면 결과가 좋게 나올 수밖에 없습니다. 테스트마다 seed를 반으로 나눠 절반으로만 학습하고, 나머지 절반에서 계획대로 실행을 뽑아 모든 bin을 채우는지 셌습니다 (분할 20번 × 추출 200번).

xcrg 2022.2 텍스트 보고서의 문제 3가지를 파서에서 처리했습니다: 두 번째 cross 표가 첫 번째 표의 내용으로 중복 출력됨, 못 친 cross bin이 (a b)·*로 묶여 나옴, weight 0인 참고용 cross가 섞여 있음.

08 · Embedded C

ARM bare-metal C로 HW/SW co-verification

JTAG로 레지스터를 직접 쓰는 시험은 하드웨어만 확인합니다. 실제 드라이버 경로까지 확인하려고, 같은 7개 시험을 Cortex-A9에서 도는 C 프로그램(Vitis standalone BSP)으로 다시 만들었습니다. 프로그램이 데이터를 준비하고, DMA를 구동하고, 결과를 스스로 판정합니다.

cache coherency 처리

DMA가 연결된 HP0 포트는 CPU cache와 일관성을 보장하지 않습니다. 참조 C 예제는 D-cache를 통째로 껐지만, 이 프로그램은 cache를 켠 채로 필요한 범위만 처리합니다.

  • DMA 전: 원본과 대상 범위를 Xil_DCacheFlushRange로 DDR에 내보냄 (대상의 dirty line이 DMA 결과를 덮지 않게)
  • 레지스터 설정 → IDLE 확인 → ap_start → DONE 대기 (1초 넘으면 HANG)
  • DMA 후: 대상 범위를 Xil_DCacheInvalidateRange로 비우고 바이트마다 비교

결과 두 경로로 교차 확인

프로그램은 결과를 UART로 출력하고, 같은 내용을 DDR의 mailbox 구조체에도 씁니다. 호스트 스크립트는 JTAG로 mailbox를 읽고 UART 로그와 판정이 같은지 확인합니다. 둘이 다르면 전체를 실패로 처리합니다.

  • xsct: XSA → standalone BSP → ELF 빌드
  • xsdb: 비트스트림, PS 초기화, ELF 다운로드와 실행
  • Python: mailbox 해석, UART 수신, 판정, result.json
